# 空室確認 と 類似物件（あとで）ボタン 仕様メモ

LINE公式アカウントの「空室確認」フローと、その結果として送られる
「ご案内が難しい状況でした」メッセージ／類似物件の提案について。
このファイル単体で挙動が分かるように書いてある。

関連ファイル：`~/コード.js`（入口・状態管理）、`~/ExistingBot.js`（検索・遅延返信）
反映には **GASデプロイが必要**（`bash gas_deploy.sh ~`）。

---

# 第1部：空室確認

## 1. 顧客から見た流れ

```
顧客: 「空室確認」（リッチメニュー or テキスト）
  ↓
Bot: 空室確認を承ります。
     以下のいずれかをお送りください：
     ・物件名（例: ○○マンション101）
     ・所在地（例: 渋谷区神宮前）
     ・最寄駅（例: 新宿駅）
     ・専有面積（例: 25.5）
     ・募集ページのURL
  ↓
顧客: SUUMOのURL / 物件名 など
  ↓
Bot: 物件カードのカルーセル（ヒットした物件を最大12件）
```

## 2. 入力の受け付け方

`handleVacancyQuery()`（ExistingBot.js）が以下の順で照合する。前段でヒットしたら後段は見ない。

| 順 | 種別 | 判定 |
|---|---|---|
| 1 | SUUMO URL / bc番号 | `bc_100517613276` 等を抽出して J列と部分一致 |
| 2 | 専有面積 | `24` `24.32` `24m²` `24平米` 等を数値化して**完全一致** |
| 3 | 自由テキスト | 物件名+部屋番号 / 所在地 / 最寄駅 に**双方向の部分一致** |

**双方向の部分一致**とは、`シート値.indexOf(入力)` だけでなく `入力.indexOf(シート値)` も見るということ。
顧客が「物件名：VIVACE301（改行）最寄り駅：…」のようなラベル付き複数行で送ってくると、
入力のほうがシート値より長くなり片方向では絶対にマッチしないため。
加えてラベル付き入力は `extractStructuredValues()` で値だけを抜き出して個別にも照合する。

## 3. 結果ごとの分岐

### ヒット（1〜12件）

物件カードのカルーセルを返し、**その時点で空室確認モードを抜ける**。

各物件はシートのステータス（I列）で扱いが分かれる。

| ステータス | 挙動 |
|---|---|
| `募集中` | カードに「募集中」表示。以降なし |
| `要確認` | カードに「スタッフが確認中です」。**Discordへ確認依頼**を飛ばす（下記） |
| それ以外（募集終了等） | **遅延返信キュー**に入り、数分後に「ご案内が難しい」旨を自動送信（第2部） |

### 0件

**1回で空室確認モードを終了**し、やり直しボタンを出す。

```
「あいうえお」では該当する物件が見つかりませんでした。

もう一度お調べする場合は、下のボタンをタップしてください。
[🏠 もう一度空室確認]
```

以前は「3回外したら自動終了」だったが、同じ案内が繰り返されてループ感があるうえ、
回数を稼ぐ間ずっとモードが生きるため無関係なメッセージを拾い続けていた（2026-08-01 変更）。

### 13件以上

件数だけ返して絞り込みを促す。この時はモードを継続する（中止ボタンつき）。

## 4. 「要確認」物件の Discord 通知とスタッフ返信

REINS 等で自動判定できない物件は `要確認` にしてあり、顧客には「スタッフが確認中です」とだけ見せて、
**担当者向けDiscordに確認依頼**を出す。

```
🔔 空室確認依頼（要確認物件）
お客様: 庄司 みのり 様 が空室確認を希望しています。
━━━━━━━━━━━━━━━━
**イニシアイオ高田馬場 601号室**
所在地: 新宿区高田馬場3（下落合駅）
賃料 15.4万円 / 1LDK / 35.21m²
📋 物件番号検索: <REINSの検索リンク>
🟢 [このお客様に「募集中」と返信](...&status=available)
🔴 [このお客様に「ご案内不可」と返信](...&status=closed)

→ 元付業者に確認のうえ、上のボタンでお客様にLINE返信してください。
```

このリンクは `action=staff_reply_vacancy` のGASエンドポイントで、**押すとその顧客にLINEが飛ぶ**。

### ⚠️ 過去の事故（2026-07-31 修正済み）

要確認物件が **Discordに出すのと同時に遅延返信キューにも入っていた**ため、
スタッフが確認する前に約4分後「ご案内不可」が顧客へ自動送信されていた。
現在は `要確認` は遅延キューに入れない（手動返信のみ）。

## 5. モードの安全装置（2026-08-01 追加）

空室確認モードは無関係なメッセージを検索クエリとして拾ってしまうため、3重に塞いである。

1. **ヒット確定の直後にモードを抜ける**
   以前は返信・キュー追加・Discord通知（最大3回リトライ）が全部終わった関数の最後で解除していたため、
   その数十秒の隙に届いたメッセージが検索に回っていた
2. **相槌はクエリとして扱わない**（`isVacancyFillerText`）
   「おねがいします」「ありがとうございます」「はい」「了解です」等は検索も返信もせず無視する。
   ただし完全一致のみなので「お願いします イニシアイオ高田馬場601」は通常どおり検索される
3. **モードに30分の有効期限**（`VACANCY_MODE_TTL_MS`）
   開始したまま放置されたモードが、後日の雑談を検索に回すのを防ぐ

### この3つが無かった頃に起きた事故

```
14:12 客: https://suumo.jp/chintai/bc_100517613276/
14:13 Bot: [物件カード] スタッフが確認中です
14:13 客: おねがいします
14:13 Bot: 該当する物件が見つかりませんでした   ← 矛盾
```

## 6. 物件ページ側の「空室確認」ボタンについて

顧客向け物件ページにもテストユーザー限定の「空室確認」ボタンがあったが、
**申込・内見と並ぶと何のボタンか分かりにくかったため 2026-08-01 に非表示にした。**

`docs/property.html` にコメントアウトで残してあり、その1行を戻せば復活する。
呼び出し側（`loadInitialAvailabilityStatus` 等3箇所）はいずれも要素が無くても
null チェックで素通りするので、他への影響はない。

# 第2部：「ご案内が難しい」メッセージと 類似物件（あとで）ボタン

## 1. いつ送られるか

空室確認で **募集終了などの物件がヒットしたとき**、その場では返さず
`enqueueDelayedReply()` で「返信キュー」シートに積み、後から push 送信する。

即答しないのは、**確認しているように見せるため**。

| 受付時刻 | 送信予定 |
|---|---|
| 営業時間内（10〜20時） | **2〜8分後**（ランダム） |
| 営業時間外 | 翌営業日の **10:16〜10:33** |

送信予定が営業時間外にはみ出す場合は翌朝へ繰り延べる。
同じ `userId + 物件名 + 部屋番号` で `pending` があれば重複追加しない。
実際の送信は5分間隔の定期トリガー `processReplyQueue()` が行う（営業時間外は何もしない）。

## 2. 送られる内容（条件登録の有無で分岐）

### 既に検索条件を登録済みの顧客 → テキストのみ

```
お待たせいたしました。
「イニシアイオ高田馬場 601」について確認いたしましたが、
現在ご案内が難しい状況でした。

引き続き、ご希望の条件に合うお部屋が見つかり次第すぐにご案内いたします。
```

既に条件が入っているので、改めて条件登録に誘導する必要がない。

### まだ条件未登録の顧客 → Flex で2択

```
┌────────────────────────────┐
│ 確認結果のお知らせ            │
│                            │
│ 「イニシアイオ高田馬場 601」は、│
│ 今回はご案内が難しい状況でした。│
│                            │
│ よろしければ、ご希望に近いお部屋を│
│ こちらでお探ししてお知らせします。│
├────────────────────────────┤
│ [   お部屋を探す   ]  ← 緑    │
│ [     あとで      ]  ← グレー │
└────────────────────────────┘
```

- **「お部屋を探す」** → `条件登録` を送信 → 条件登録フローが始まる
- **「あとで」** → `類似物件不要` を送信

## 3. 「あとで」（類似物件不要）を押したとき

`コード.js` でこのテキストを受け、次を返して終わる。

```
承知いたしました。
またお部屋探しの際はお気軽にお声がけください。
```

**それだけ。** 状態は持たず、配信停止も条件登録も起きない。
以降も普通に「空室確認」や「条件登録」を使える。

つまり「あとで」は**断りではなく、その場の会話を静かに閉じるための出口**。
押しても不利益が無いので、顧客が既読スルーせずに済む。

---

## 4. 触るときの注意

- **`要確認` を遅延キューに入れないこと。** 入れるとスタッフ未対応のまま
  「ご案内不可」が顧客へ自動送信される（第1部の事故）
- **「あとで」に副作用を足さないこと。** 配信停止などに繋げると、
  軽い気持ちで押した顧客の配信が止まる
- 遅延返信の待ち時間をゼロにしないこと。即答すると自動送信だと分かってしまう
