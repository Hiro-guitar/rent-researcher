# おすすめ条件（裏条件）仕様メモ

お客さんが登録した検索条件とは**別に、こちら（仲介側）が設定する検索条件**。
「エリアを広げた案」「賃料を上げた案」のように、**1顧客に何本でも**持てる。

お客さんには**一切見えない。** 通知される物件は本人条件で見つかったものと区別なく届く。
だから「裏条件」と呼んでいる。

実装：`~/RecommendCriteria.js`（651行・ほぼ1ファイルで完結）
UI：`~/CustomerPage.html`（顧客詳細の「🎯 おすすめ検索条件（裏条件）」）
反映には **GASデプロイが必要**（`bash gas_deploy.sh ~`）。

---

## 1. 何のためにあるか

お客さんの登録条件は、本人が書いたとおりに扱いたい。**こちらが勝手に書き換えない**のが原則。
一方で実務上は「この条件だと出てこないから、少し広げて探したい」がほぼ毎回ある。

- 本人条件を直接いじる → 顧客の意思を上書きすることになる。条件変更履歴も汚れる
- 何もしない → 紹介できる物件が無いまま止まる

そこで**別シートに、こちら専用の条件を持つ**。本人条件は無傷のまま、自動検索は両方を回す。

**顧客に「条件を変えませんか」と提案する仕組み（`SPEC_条件変更提案.md`）とは別物。**
あちらは顧客に動いてもらう導線、こちらはこちらだけで完結する。

---

## 2. データの持ち方

**おすすめ検索条件シート**（検索条件シートと同じスプレッドシート内）。

列の並びは**検索条件シートとわざと同じ**にしてある。パース処理を共通化するため。

| 列 | 内容 |
|---|---|
| A〜R | 検索条件シートと同じ（顧客名・市区町村・路線・賃料・間取り…） |
| Y(24) | 町名丁目JSON |
| AA(26) | 入居時期厳守 |
| AC(29) | 最終REINS検索日 |
| **AE(31)** | BT別モード（`skip` / `alert`） |
| **AH(34)** | **ラベル**（「エリアを広げた案」など） |
| **AI(35)** | **ID**（本人条件と区別する識別子） |
| **AJ(36)** | 有効フラグ（`0` で無効） |
| AK(37) | 独立洗面台モード（`skip` / `alert`） |
| AL(38) / AM(39) | 希望階数 / 部屋番号の数字合計 |
| AN(40) / AO(41) | 車種 / 最低階数 |

シートが無ければ `_getRecommendSheet_()` が**自動で作ってヘッダーを入れる**。

## 3. 作り方・編集の仕方（CRMから）

顧客詳細ページの「🎯 おすすめ検索条件（裏条件）」セクションで操作する。

```
＋ おすすめ条件を追加
  ↓ 名前を聞かれる（例：「エリアを広げた案」）
条件フォーム（criteria.html）が開く
  ↓ 初期値は【お客さんの現在の条件】が全項目入っている
広げたい項目だけ直して保存
```

新規作成時に本人条件をシードするのが肝。**ゼロから入れ直すのではなく「本人条件を緩める」**
という作業になるので早い（`42faa1e`）。

### 仕組み上のポイント：`rec::` トークン

条件フォームは顧客用のものをそのまま流用している。顧客と区別するために、
`userId` に **`rec::<トークン>`** という偽のIDを渡す。

```
startRecommendEditor()
  → state を rec::<token> で保存（30分キャッシュに顧客名・ID・ラベルを持つ）
  → フォームのURLを返す
フォーム送信 → processCriteriaSelection が rec:: を見て
  → _saveRecommendFromForm_() へ分岐（顧客の条件には一切触れない）
```

⚠️ **セッションは30分。** 切れると「セッションが切れました」となり、開き直しが必要。

⚠️ **条件フォームには入居時期の入力欄が無い。**
そのためシード元（本人条件 or 編集元のおすすめ条件）から引き継いでいる。
入居時期はシート上でのみ編集する（CRMの「📅 入居時期: 設定」）。

### できる操作

| 操作 | 関数 |
|---|---|
| 一覧 | `listRecommendCriteria(customerName)` |
| 追加・編集 | `startRecommendEditor` → フォーム → `_saveRecommendFromForm_` |
| 名前の変更 | `renameRecommendCriteria(id, newLabel)` |
| 有効/無効 | `setRecommendEnabled(id, enabled)` |
| 削除 | `deleteRecommendCriteria(id)` |
| 入居時期 | `setRecommendMoveIn(id, date, strict)` |
| BT別 / 独立洗面台のモード | `setRecommendBtMode` / `setRecommendSenmenMode` |
| **その条件で検索ページを開く** | `openRecommendSearch(id, service)` / `openRecommendSearchAll(id)` |

最後のものは自動検索とは別で、**その場で REINS / いえらぶ / itandi / いい生活 の
検索ページを条件入りで開く**手動用。「まとめて開く」で4サービス同時に開く。

## 4. 自動検索にどう乗るか

拡張が条件を取りに来る（`handleGetCriteria`）とき、本人条件を組み立てた**後**に
`_appendRecommendCriteria_()` が同じ配列へ追記する。以降は本人条件と**完全に同格**に扱われる。

```js
criteriaArr.push({
  name: name,            // ← 顧客名は本人と同じ
  ...条件...,
  recommend: true,       // これが目印
  recommendId: '...',
  recommendLabel: 'エリアを広げた案'
});
```

### 検索対象に入る条件

1. 顧客が**配信対象**であること（`deliverableNames`）。
   顧客を配信停止・ブロック・スヌーズすると、**おすすめ条件も一緒に止まる**
2. 有効フラグが `0` / `false` でないこと
3. **条件が空でないこと**（市区町村・路線・駅・賃料・間取り・面積・築年数・町名のどれか）。
   全部空のまま検索すると全件ヒットして暴走するため

### 拡張側での扱い

- 条件のキーは **`rec::<recommendId>`**（本人条件は顧客名そのもの）。
  これで本人条件とおすすめ条件を**独立してON/OFF**できる
- 拡張のダッシュボードでは顧客の枠の中に `↳ おすすめ: <ラベル>` として並ぶ
- **最終REINS検索日はおすすめ条件ごとに独立して記録**される
  （`update_reins_search_date` に `recommend_id` を付ける）。
  本人条件の検索日を消費しない
- ログには `顧客名(おすすめ: ラベル)` と出る

### ⚠️ 新しい条件は既定OFF

拡張の顧客フィルタは「**新しく現れた条件は既定でOFF**」。
おすすめ条件を作っただけでは検索は走らない。**ダッシュボードでチェックを入れて初めて動く。**

## 5. お客さんからどう見えるか

**見えない。**

- おすすめ条件で見つかった物件も、通知は通常どおり顧客のLINEへ届く
- 「おすすめ条件で見つけました」といったラベルは付かない
- 顧客の登録条件（検索条件シート）は**1文字も変わらない**
- 条件変更履歴にも残らない（本人が変えたわけではないため）

既送信の判定は**顧客名を軸に**行われ（部屋ID＋「住所・部屋番号・面積・間取り」から作る
dedupキーの2本立て）、おすすめ条件も顧客名は本人と同じなので、
**本人条件とおすすめ条件の両方でヒットしても二重に届くことはない。**

---

## 6. BT別 / 独立洗面台のモード

「バス・トイレ別」「独立洗面台」は物件データに載っていないことが多く、
条件に入れると母数が激減する。そこで**おすすめ条件ごとに扱いを選べる**ようにしてある。

| モード | 挙動 |
|---|---|
| `skip` | 条件を満たさない物件を**除外する**（選別） |
| `alert` | **除外せず**、担当者向けにアラートだけ出す |

- **こだわりに該当項目が入っている時だけ**有効になる。入っていなければ空＝勝手に絞らない
- 既定は **BT別 = `skip`**、**独立洗面台 = `alert`**
  （独立洗面台は情報の欠落が多く、skipだと取りこぼしが大きすぎたため `cc7f583` で変更）

## 7. 触るときに壊しやすい点

1. **列レイアウトを検索条件シートとズラさないこと。** パースを共通化している前提が崩れる
2. **`_saveRecommendFromForm_` で顧客の条件を書かないこと。**
   `rec::` の分岐を外すと、おすすめ条件の保存が**本人条件の上書き**になる
3. **空条件のガードを外さないこと。** 全件ヒットで暴走する
4. **`deliverableNames` のゲートを外さないこと。**
   配信停止した顧客におすすめ条件だけ動き続ける状態になる
5. **`recommendId` をキーに使っている。** IDを振り直すと、
   拡張側のON/OFF設定と最終検索日が紐付かなくなる（別条件として扱われ既定OFFに戻る）
6. **編集セッションは30分。** フォームを開いたまま放置すると保存できない
