# 条件変更提案 仕様メモ

条件は登録しているのに**物件が届いていない／届いても見ていない**顧客に、
「条件を少し緩めませんか」とLINEで提案する仕組み。

反応が無いまま3回目まで行くと**配信を続けるかどうかの確認**に切り替わり、
それも無視されたら**自動で配信停止**する。放置アカウントに永久に送り続けないための出口。

このファイル単体で挙動が分かるように書いてある。

実装：`~/ConditionSuggestion.js`（1ファイルで完結）
反映には **GASデプロイが必要**（`bash gas_deploy.sh ~`）。

---

## 1. 全体像

```
毎日 10:00 (JST) のトリガー
  ↓ runConditionSuggestionAutoSend()
① 確認メッセージを24時間無視した人を自動停止  （_autoPauseExpiredConfirmations_）
② 候補を抽出                                （getConditionSuggestionCandidates_）
③ 全員に送信                                （sendConditionSuggestionMessages）
④ 結果をDiscordに通知                        （_notifyAutoSendToDiscord_）
```

送るメッセージは**連続送信回数（AD列）で切り替わる**。

| 回数 | 送るもの |
|---|---|
| 1回目・2回目 | 条件変更提案カード（現在の条件一覧＋3ボタン） |
| 3回目 | **配信継続の確認カード**（提案ではなく「続けますか？」） |
| 3回目のまま24時間 | 送らない。**配信ステータスを `auto_paused` にする** |

顧客がどれかのボタンを押すと**カウントは0に戻る**ので、反応がある限り自動停止しない。

---

## 2. 誰に送るか（候補の条件）

`getConditionSuggestionCandidates_()` が全部を判定する。**すべて満たす必要がある。**

1. 配信ステータス（S列）が `active`（`paused` / `snoozed` / `blocked` / `auto_paused` は除外）
2. LINE userId が紐付いている（無ければ送れないのでスキップ）
3. **オプトアウトされていない**（§6）
4. 前回の提案送信（Z列）から **10日以上**経過
5. 下の **ケースA / ケースB のどちらか**に当てはまる

### ケースA `no_delivery` — 物件が届いていない

最終物件通知日から10日以上経過。通知が一度も無ければ**登録日**から数える。
フローが止まっている人。

### ケースB `no_view` — 届いているのに見ていない

次の3つを同時に満たす場合。

- 登録から10日以上経過（登録直後に判断するのは早すぎる）
- 物件が**直近10日以内に送信されている**
- 閲覧履歴が無い、または最終閲覧から10日以上経過

「送っているのに開かれていない」＝条件が合っていない可能性が高い、という読み。

閾値は `CONDITION_SUGGESTION_THRESHOLD_DAYS = 10` の1箇所で決まる。

> ⚠️ **コード内のコメントに「14日」と書かれている箇所が残っているが、実際は10日。**
> 14→10 に変えた時（`aacc09e`）にコメントを直し忘れている。定数を見ること。

### 参照するデータ

| 判定材料 | 出どころ |
|---|---|
| 最終物件通知日 | 承認待ち物件シート（`status='sent'` の最新） → `_buildLastDeliveryMap_` |
| 最終物件閲覧日 | アクションログの `view` 行 → `_buildLastViewMap_` |
| 登録日 / 現在の条件 / ステータス | 検索条件シート |

並び順は**経過日数が多い順**。

## 3. 送るメッセージ

### 1回目・2回目：条件変更提案カード

```
┌──────────────────────────────┐
│  ご条件の変更をしてみませんか？   │ ← 緑ヘッダー
├──────────────────────────────┤
│ 条件を少し緩めると、ご紹介できる   │
│ 物件が増える可能性があります。     │
│ ┌──────────────────────────┐ │
│ │ 現在ご登録の条件            │ │
│ │ 家賃の上限  12万円          │ │
│ │ 沿線・駅   ＪＲ中央線(吉祥寺) │ │
│ │ 間取り     1LDK            │ │
│ │ 専有面積   30m² 以上        │ │
│ │ 築年数     20年以内         │ │
│ │ 駅徒歩     7分以内          │ │
│ │ こだわり   バス・トイレ別     │ │
│ └──────────────────────────┘ │
├──────────────────────────────┤
│ [    条件を変更する    ]        │ ← 条件フォーム(LIFF)へ
│ [  このまま様子を見る  ]        │
│ [    配信を停止する    ]        │
└──────────────────────────────┘
```

**ケースBの人は文面が変わる。** 物件は届いているので「緩めませんか」では噛み合わないため。

| | ケースA（no_delivery） | ケースB（no_view） |
|---|---|---|
| タイトル | ご条件の変更をしてみませんか？ | お部屋探しの状況はいかがですか？ |
| 本文 | 条件を少し緩めると、ご紹介できる物件が増える可能性があります。 | もしピンとくるものがなければ、条件を少し変えると、よりご希望に合うお部屋が見つかるかもしれません。 |

条件の一覧は**空でも「指定なし」と必ず表示する**。顧客が自分の登録状態を完全に把握できるようにするため。

### 3回目：配信継続の確認カード

```
┌──────────────────────────────┐
│ お部屋探しの状況はいかがですか？   │
├──────────────────────────────┤
│ なかなかピンとくるお部屋が        │
│ 見つからない場合は、条件を少し     │
│ 変えてみると新しい物件が          │
│ 見つかるかもしれません。          │
│                              │
│ 引き続き物件情報をお届けしても     │
│ よろしいですか？                │
├──────────────────────────────┤
│ [    条件を変更する    ]        │
│ [ このまま配信を続ける  ]        │
│ [    配信を停止する    ]        │
└──────────────────────────────┘
```

条件の一覧は載せない。ここで聞きたいのは条件ではなく**続けるかどうか**なので。

## 4. ボタンを押したとき（`handleConditionSuggestionPostback`）

**どのボタンでも、まず連続送信カウント（AD列）を0にリセットする。**
反応があった時点で「無視されている」ではないため。

| postback | 挙動 |
|---|---|
| `condsug:change` | `startChangeFlow` を呼ぶ（条件変更フロー） |
| `condsug:continue` | 「承知いたしました。引き続き…」と返して終了 |
| `condsug:keep` | 同上＋「気が変わった時は『条件変更』とお送りください」 |
| `condsug:pause` | `handleDeliveryStopCommand` に委譲（**理由を聞くquickReplyが出る**） |

「条件を変更する」ボタン（1・2回目のカード）だけは postback ではなく**LIFFのURI**で、
条件フォームを直接開く。URLには条件が埋め込まれる（`_criteriaStateParam_`）ので
フォームはGASを呼ばずに即描画される。

---

## 5. 押されなかったとき（自動停止）

`_autoPauseExpiredConfirmations_()` が毎日の実行の**最初**に走る。

```
AD列（連続送信回数）>= 3  かつ  Z列（最終送信日）から24時間経過
  → S列を 'auto_paused' にする
```

`auto_paused` になると配信ステータスが `active` でなくなるので、
**候補抽出からも物件配信からも外れる。** 顧客側には何も送らない。

⚠️ カウントが3以上の人は `sendConditionSuggestionMessages` 側でも
「確認メッセージ応答待ち」としてスキップされる。**24時間チェックだけが次の処理を決める。**

---

## 6. 止める手段（3種類ある）

| 手段 | 効き方 | 設定場所 |
|---|---|---|
| **顧客ごとのオプトアウト** | その顧客だけ、候補抽出からも管理画面の候補一覧からも消える | 顧客詳細のトグル → `setConditionSuggestionOptOut` → ScriptProperties `CONDITION_SUGGESTION_OPTOUT`（顧客名のJSON配列） |
| **機能全体の無効化** | 自動送信を丸ごとスキップ（手動送信は可能） | ScriptProperties `CONDITION_SUGGESTION_AUTO_ENABLED = 'false'` |
| **配信ステータス** | `active` 以外なら対象外 | 検索条件シート S列 |

---

## 7. 使っている列

検索条件シートに3列。**列番号を動かすと壊れる。**

| 列 | 定数 | 用途 |
|---|---|---|
| **Z列（26）** | `CONDITION_SUGGESTION_SENT_COL` | 最終送信日時。空欄＝未送信 |
| **AD列（30）** | `CONDITION_SUGGESTION_COUNT_COL` | 連続送信回数。反応があると0に戻る |
| S列（19） | — | 配信ステータス。自動停止時に `auto_paused` を書く |

⚠️ **AD列は条件変更が保存された時にも0にリセットされる**（`SheetWriter.js` の `writeToSheet`）。
条件を変えた＝反応した、という扱い。

---

## 8. Discord通知

自動送信のたびに結果を通知する（候補数・送信・スキップ・失敗・自動停止人数）。
致命的なエラーが出た場合も別途通知する（`_notifyAutoSendErrorToDiscord_`）。

**自動停止だけが発生して候補が0人の場合も通知する。** 黙って人が止まるのを避けるため。

---

## 9. 手動送信・テスト・セットアップ

| 関数 | 用途 |
|---|---|
| `listConditionSuggestionCandidates()` | 管理ページ「条件変更提案」の候補一覧（`google.script.run` から） |
| `sendConditionSuggestionMessages(names)` | 指定顧客に送信。自動送信もこれを呼んでいる |
| `sendConditionSuggestionTest(name, reasonCode)` | テスト送信。`reasonCode` で ケースA/B・確認メッセージを出し分けられる |
| `setupConditionSuggestionAutoTrigger()` | **毎日10:00のトリガーを登録する。1回だけ手動実行する** |
| `checkConditionSuggestionTrigger()` | トリガーが生きているか確認 |
| `checkSuggestionIgnoreStatus()` / `backfillSuggestionCounts()` | 一時ユーティリティ。AD列を後から埋めるために作ったもの |

トリガーはコードに書いてあるだけでは動かない。**`setupConditionSuggestionAutoTrigger()` の手動実行が必要。**

## 10. 触るときに壊しやすい点

1. **閾値は定数1箇所**（`CONDITION_SUGGESTION_THRESHOLD_DAYS`）。
   コメントの「14日」は古い記述なので信用しない
2. **AD列のリセットを消さないこと。** 反応した人が3回で自動停止される
3. **`auto_paused` を `active` に戻すのは手動。** 自動では復帰しない
4. **`condsug:pause` を直接「配信停止」にしないこと。**
   `handleDeliveryStopCommand` に委譲して**理由を聞く**のが現仕様。理由は追客の材料になる
5. **条件の一覧から項目を減らさないこと。** 「指定なし」も含めて全項目出すのが意図
6. **旧仕様のコードが大量に残置されている**（下記）。消さないよう注意

### 残置されている旧仕様

以前は「サクッと変更」として、カード上に**家賃／築年数／面積／駅徒歩／間取り／構造／こだわり**の
ボタンを並べ、LINE内で値の選択まで完結させていた。現在そのボタンは出していないが、
**ハンドラと値選択ロジックは丸ごと残してある。**

```
_buildValueSelectionFlex_ / _applyConditionChange_
_findNearestSmallerLayouts_ / _generateRelaxCumulativeOptions_
_parseLayout_ / _CONDSUG_INPUT_PROMPT
_enterConditionInputMode_ / handleConditionSuggestionTextInput
handleConditionSuggestionPostback の condsug:open / condsug:set / condsug:input
```

理由は2つ。**過去に送信したメッセージの古いボタンが今でもタップされうる**こと、
そして次に仕様を変える時に再利用するため。
