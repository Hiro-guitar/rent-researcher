# 空室確認からの条件登録 仕様メモ（2026-08-05〜08-06 実装）

空室確認で「募集終了だった」と分かった物件のスペックから**検索条件を組み立てて提示し、
そのまま登録まで持っていく**仕組み。以前の「類似物件を希望しますか？」の2択を置き換えた。

このファイル単体で経緯と挙動が分かるように書いてある。

関連ファイル：`~/ExistingBot.js`（条件の生成・カード）、`~/コード.js`（postback）、
`~/ConversationFlow.js`（追加質問）、`~/SheetWriter.js`（保存）
反映には **GASデプロイが必要**（`bash gas_deploy.sh ~`）。

> 旧仕様（「お部屋を探す / あとで」の2択）は `SPEC_空室確認と類似物件.md` の第2部に
> 書かれているが、**そこは現在の実装と違う**。空室確認そのもの（第1部）は今も有効。

---

## 1. なぜ変えたか

置き換え前は、条件未登録の顧客にこう出していた。

```
┌────────────────────────────┐
│ 確認結果のお知らせ            │
│ 「◯◯マンション 601」は、      │
│ 今回はご案内が難しい状況でした。│
│                            │
│ よろしければ、ご希望に近いお部屋を│
│ こちらでお探ししてお知らせします。│
├────────────────────────────┤
│ [   お部屋を探す   ]          │
│ [     あとで      ]          │
└────────────────────────────┘
```

「あとで」は**副作用ゼロの出口**として意図的に用意したものだったが、
押した人はそのまま音沙汰なく消えていた。空室確認をしてきた＝**今まさに部屋を探している人**
なので、ここで取りこぼすのが一番もったいない。

一方で「お部屋を探す」を押しても、そこから条件登録フォームを最後まで埋める必要があり、
心理的な段差が大きかった。

そこで、**こちらが条件を作って見せ、「はい」だけで登録が終わる**形にした。
顧客が自分で条件を決める導線（＝精度が高い）は「いいえ」として残し、潰していない。

## 2. 全体の流れ

```
空室確認で募集終了の物件がヒット
  ↓ （遅延返信キューに入る。2〜8分後 / 営業時間外なら翌朝）
物件のスペックから条件を組み立てる
  ↓
┌─ 組み立てできた（条件未登録の顧客）
│    「確認結果のお知らせ」＋条件の一覧＋2択カード
│      ├ はい、お願いします      → 条件を登録 → 追加質問4問 → サマリー
│      └ いいえ、条件を自分で決める → 通常の条件登録フロー
│
└─ 組み立てできなかった / 既に条件登録済み
     従来どおりのメッセージ（登録済みなら誘導なしのテキストのみ）
```

遅延返信の仕組み（キュー・送信時刻）は旧来のままなので `SPEC_空室確認と類似物件.md` を参照。

## 3. 条件の作り方（`_propertyToCriteria_`）

### 3-1. データの出どころ

**2つのシートを合わせる。** 片方だけでは足りない。

| 項目 | 出どころ |
|---|---|
| 賃料 / 管理費 / 間取り / 専有面積 / 最寄り駅 | 物件空室管理シート（`PROPERTY_SHEET_ID`） |
| **徒歩分数 / 築年数 / 路線名 / 設備** | **SUUMO掲載管理シート**（`_findListingSpecs_`） |

⚠️ **徒歩・築年数・設備は物件空室管理シートに存在しない。**
このシートは FN Forrent の一覧をスクレイプして作られており（`~/Desktop/suumo_auto_sheet`）、
元の一覧にこれらの列が無いため。SUUMO掲載管理シートは入稿時に埋まる。

掲載管理に無い物件（SUUMO未入稿）は徒歩・築年数・設備が取れないが、
賃料と駅があれば条件は作れる。**駅も賃料も取れない場合だけ諦める**（`return null`）。

### 3-2. SUUMOの選択肢に丸める

作った条件は最終的にSUUMOで検索されるので、**SUUMOの検索フォームに存在する値**にしか丸めない。
「築33年以内」「徒歩21分以内」のような選べない条件を作らないため。

```js
SUUMO_RENT_STEPS = 3.0〜20.0（0.5万刻み）, 21〜30（1万刻み）, 35, 40, 50, 100  // 万円
SUUMO_WALK_STEPS = [1, 5, 7, 10, 15, 20]                    // 分以内
SUUMO_AGE_STEPS  = [1, 3, 5, 7, 10, 15, 20, 25, 30]         // 年以内
SUUMO_AREA_STEPS = [20,25,30,35,40,45,50,55,60,65,70,80,90,100]  // m²以上
```

丸め方は2種類だけ。**4項目とも「ちょうど選択肢と同じ値なら、その値をそのまま使う」**。

| 種別 | 対象 | 規則 | 例 |
|---|---|---|---|
| 上限系 | 賃料・徒歩・築年数 | その物件が満たす**最小**の選択肢 | 14.8万→15万 / 15.0万→**15万** / 徒歩7分→7分以内 / 築16年→20年以内 |
| 下限系 | 専有面積 | その物件が満たす**最大**の選択肢 | 25.07m²→25 / 25.0m²→**25** / 24.99m²→20 |

選択肢の範囲外（賃料100万超・築31年など）は `null` ＝**「指定しない」**にする。

⚠️ **余裕を足してから丸めないこと。** 以前は +3分 / +5年 / −10% を加算してから丸めていて、
丸めと二重になり「築16年 → 築25年以内（実質+9年）」のように緩くなりすぎていた。
緩め方は「選択肢を1段階だけ」で統一してある（`d9764dc`, `c33f6cf`）。

### 3-3. 項目ごとの細かい規則

- **賃料上限** = 賃料 **＋ 管理費** を丸める。実際に払う額で探すため
- **徒歩** — 掲載管理から取れない場合は **10分**（グリッド上の値）を使う。
  推測値なのでこれ以上緩めない
- **間取り** — 物件のものをそのまま1つだけ
- **設備** — **「バス・トイレ別」「独立洗面台」の2つだけ**引き継ぐ。
  この2つは条件に入れる人が非常に多く、無いと的外れな物件が届く。
  それ以外を入れると絞りすぎて0件になりやすい
  - ⚠️ **表記ゆれに注意**。SUUMOは「バストイレ別」「洗面所独立」、
    REINS/itandi等は「バス・トイレ別」「独立洗面台」と書く。判定は両方に対応済み
- **その他ご希望（notes）** — **必ず空にする**。顧客が自分で書く欄なので、
  こちらで「空室確認で◯◯を見たため」等を書き込まない（`cde0d5e`）
- **駅・路線** — ⚠️ 物件シートのD列は `ＪＲ総武線/小岩` という**路線と駅がくっついた形式**。
  `_splitRouteStation_` で必ず分解してから使う。分解を忘れると拡張側で
  「⚠️ 駅名解決失敗: ＪＲ総武線/小岩」になり検索できない（`e26742b`）

## 4. 提示するカード

```
┌──────────────────────────────┐
│ 確認結果のお知らせ              │
│ 「ディナック吉祥寺 309号室」は、  │
│ 今回はご案内が難しい状況でした。   │
│                              │
│ ご覧のお部屋に近い条件で、        │
│ お探しできます。                │
│ ┌──────────────────────────┐ │
│ │ 沿線・駅   ＪＲ中央線（吉祥寺）│ │
│ │ 家賃の上限  15万円           │ │
│ │ 間取り     1LDK             │ │
│ │ 専有面積   30m²以上          │ │
│ │ 築年数     20年以内          │ │
│ │ 駅徒歩     7分以内           │ │
│ │ こだわり   バス・トイレ別、    │ │
│ │           独立洗面台         │ │
│ └──────────────────────────┘ │
│ この条件でお探ししますか？        │
├──────────────────────────────┤
│ [    はい、お願いします    ]    │ ← 緑ベタ塗り
│ [ いいえ、条件を自分で決める ]   │ ← スレートグレー・同じ高さ
└──────────────────────────────┘
```

「合っていますか」ではなく「**お探ししますか**」にしている。
この条件は顧客自身が一度も言っていない推測値なので、合否を尋ねる形だと違和感が出るため。

### ⚠️ ボタンのデザインで失敗した2案（戻さないこと）

| 案 | 何が起きたか |
|---|---|
| 「はい」だけ緑ベタ塗り、「いいえ」は文字リンク | 「はい」への誘導になる。推測条件を勢いで承認させると精度の低い条件が登録され、本来もっと良い「自分で決める」導線を潰す |
| 両方を**枠線だけ**のボタンに | 中が抜けて見えて、ボタンだと分からない |
| 両方を**同じ緑**のベタ塗りに | 隣接して「2行の1つの文章」に見える |

**結論: サイズは揃えたまま、色だけ変える。** どちらもベタ塗りなので押しやすさは同じで、
2択だと一目で分かる（`be5f9dc`, `3de8358`）。

## 5. 「はい、お願いします」を押したあと

`action=auto_criteria&name=...&room=...` の postback を `~/コード.js` が受ける。

### 5-1. 条件を登録する（`registerAutoCriteriaFromProperty`）

- `writeToSheet` を再利用して検索条件シートの**本人の行**に書く（列の知識を1箇所に保つため）
- **既に条件がある人は上書きしない**（`already_registered` を返す）。
  連打・古いカードの再タップでの事故を防ぐ
  - テストユーザーだけ `opts.force` で通せる。⚠️ force は既存行のA〜R列を上書きする
- 書けたら **AT列（46列目）に自動登録日時**を入れる（`_markCriteriaProvisional_`）。
  「これは暫定条件」の目印

### 5-2. 自動では作れない4項目を聞く

物件からは絶対に分からない項目があるので、登録直後に質問する（`9a30175`）。

```
■■□□  2/4
どなたがお住まいになりますか？
```

順番は `FLOW_GAUGE_FOLLOWUP_ORDER`:

1. お引越しの理由
2. どなたが住むか
3. 年齢
4. 入居時期

- 前置きは付けない。**受付の一言＋ゲージ＋質問を1通にまとめる**。
  長いと読まれず、次のボタンも押されなくなる（`31e3b89`）
- 条件選択ページ（路線・賃料など）は自動で入っているので飛ばす
- 最後に**通常の条件登録と同じサマリーカード**を出す（`ecb8d65`）

### 5-3. ⚠️ 回答の保存に `writeToSheet` を使わないこと

追加質問の回答は `persistAutoFollowupAnswers` が**セル単位**で書く。

```js
if (d.reason)         _updateCriteriaCell_(name, 14, d.reason);   // N列: 理由
if (d.move_in_date)   _updateCriteriaCell_(name, 15, ...);        // O列: 引越し時期
if (d.resident)       _updateCriteriaCell_(name, 18, ...);        // R列: 居住者
if (d.move_in_strict) _updateCriteriaCell_(name, 27, 'true');     // AA列: 入居時期厳守
if (d.age)            _updateCriteriaCell_(name, 28, d.age);      // AB列: 年齢
```

ここで `writeToSheet` を使うと、**state に入っていない項目（＝自動生成した駅・賃料・間取り等）が
空で上書きされて全部消える**。追加質問の state は4項目しか持っていないため。

## 6. 「いいえ、条件を自分で決める」を押したあと

postback データは `条件登録`。`startSearchOrChangeFlow` に入る。

- **条件未登録** → 初回の質問フロー（＝実顧客が通る道）
- **条件登録済み** → 「すでに条件が登録されています」＋条件変更フロー

このカード自体が条件未登録の人にしか出ないので、**本番では必ず初回フロー**に入る。
テストユーザーは条件が登録済みで本番の導線を確認できなかったため、
`TEST_ALLOWED_NAMES` の場合だけ登録済みでも初回フローを流すようにしてある（`5855019`）。

## 7. 登録後に何が起きるか

### 担当者向けDiscord通知（必須）

⚠️ **これが無いと機能しない。**
Chrome拡張の顧客フィルタは「**新しく現れた条件は既定でOFF**」なので、
担当者がチェックを入れるまでその顧客の検索は1回も走らない。
自動登録されたことに気づけないと、条件だけ増えて誰も探されない状態になる。

通知は**その顧客のスレッド**へ、**無音**で送る（`b8ae7b2`）。

### データの残りかた

| 場所 | 内容 |
|---|---|
| 検索条件シート 本人の行 | 自動生成した条件（A〜R列）＋ 追加質問の回答（N/O/R/AA/AB） |
| 検索条件シート **AT列** | 暫定条件の自動登録日時 |
| 条件変更履歴シート | `writeToSheet` の差分検知により1行 |

## 8. テスト方法

条件登録済みだと本来の導線ではカードが出ないので、抜け道を用意してある。
`TEST_ALLOWED_NAMES`（現在 `['Hiroki']`）の顧客名でのみ動く。

```
テストカード ディナック吉祥寺 309
```
→ 登録済みでも暫定条件カードを出す。「はい」を押すと**既存条件を上書きして**通しで確認できる。

```
テスト条件登録
```
→ 登録済みでも初回の質問フローを最初から流す（ゲージの確認用）。

物件名・部屋番号は**物件空室管理シートに実在するもの**を指定すること。
徒歩・築年数・設備まで確認したい場合は、**SUUMO掲載管理シートにも載っている**物件を選ぶ。

## 9. 触るときに壊しやすい点

1. **「はい」を目立たせないこと**（§4）。提示している条件は推測値で、
   顧客が自分で決めたほうが精度は高い。どちらを選んでも前進するので誘導する理由がない
2. **`persistAutoFollowupAnswers` で `writeToSheet` を使わないこと**（§5-3）。自動生成した条件が消える
3. **既存条件を上書きしないこと**（§5-1）。force はテスト専用
4. **駅は「路線/駅」形式を分解してから使うこと**（§3-3）。忘れると検索できない条件ができる
5. **設備を2つより増やさないこと**（§3-3）。絞りすぎて0件になる
6. **その他ご希望（notes）を自動で埋めないこと**（§3-3）
7. **余裕を足してから丸めないこと**（§3-2）。丸めと二重になる
8. **Discord通知を消さないこと**（§7）。誰も検索されなくなる

## 10. 残っている課題

- **暫定条件で登録した人への再アプローチが未実装。**
  自動生成の条件は「その物件に似た部屋」でしかないので、
  数回配信した後に詳細条件を1回だけ促す導線を入れたい（現状は入れていない）
- SUUMO掲載管理シートの**路線名に不正な値**が混じっている場合がある（例:「総武中央線」）。
  数が多いようなら、掲載シートを信用せず駅マスターから路線を引く形に変える
